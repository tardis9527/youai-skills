# 产品简报：TeamLog（团队日报助手）

> 使用 Skill：[02_product-discovery](../skills/02_product-discovery.md)
> 版本：v1.0 | 日期：2025-04-15 | 节奏模式：Standard
> 本文为精简示例，仅展示产品简报（Product Brief）的最终产出结构

---

## 1. 产品背景与目标

- **为什么现在做**：中小技术团队普遍用 IM 群发日报，写的人烦、看的人不看；大模型 API 成本已降到"每团队每月几十元"量级，自动提炼在成本上第一次成立。
- **要解决的问题**：Leader 每天花 30-60 分钟读日报并手动汇总，信息还是散的；开发者花 10-15 分钟写日报，觉得纯属交差。
- **一期业务目标**：让 3-5 个真实团队连续使用 4 周，Leader 的日均信息获取时间从 30+ 分钟降到 5 分钟以内。

---

## 2. 产品定位与价值主张

- **一句话描述**：一款面向中小技术团队的 AI 日报助手，自动汇总团队进展，让管理者 30 秒掌握团队状态。
- **目标市场**：10-50 人规模的技术团队 / 研发部门
- **核心价值主张**：相比"飞书群里翻日报"，TeamLog 自动提炼关键进展、阻塞和风险并标红——**Leader 不需要读原文就能知道该管谁**。

---

## 3. 用户角色

### 角色 1：技术团队 Leader（🔴 主要）

- **是谁**：带 5-15 人团队的技术经理/CTO
- **典型画像**：30-40 岁，技术出身转管理，日常会议多，无暇逐条看日报
- **核心任务**：快速了解团队进展、识别阻塞项、向上汇报
- **当前方案**：飞书群里@全员发日报 → 手动逐条阅读 → Excel 汇总
- **最大痛点**：每天花 30-60 分钟读日报和汇总，效率极低
- **成功标准**：每天只花 5 分钟就能掌握团队状态并完成向上汇报
- **使用频率**：每日 1-2 次，每次 5-10 分钟 ✅ 高频，具备独立产品条件
- **触达渠道**：技术管理者社群、CTO 交流群、掘金/InfoQ 内容读者

### 角色 2：开发工程师（🔵 次要）

- **是谁**：一线开发者
- **核心任务**：快速完成日报填写，不想花太多时间
- **当前方案**：飞书/钉钉群里打字发日报，格式随意
- **最大痛点**：每天花 10-15 分钟写日报，觉得浪费时间
- **成功标准**：3 分钟内完成日报，系统自动关联代码提交记录
- **使用频率**：每日 1 次，每次 3 分钟
- **触达渠道**：由 Leader 自上而下带入，不单独获客

> ⚠️ 注意角色 2 是**被动用户**：他不选择这个产品，但他能毁掉它——填报体验不好，数据源就断了。

## 4. MVP 功能清单（一期必做，已按阶段五结论修正）

| 序号 | 功能 | 用户故事 | 难度 | 为什么是 MVP |
|------|------|---------|------|------------|
| 1 | 结构化日报填写 | 作为开发者，我想用模板快速填写日报，以便减少写日报的时间 | S | 核心数据入口，不做则无数据可汇总 |
| 2 | AI 日报汇总 | 作为 Leader，我想看到 AI 自动生成的团队日报摘要，以便快速了解进展 | M | 产品核心价值，不做则与飞书群无差异 |
| 3 | 进度看板 | 作为 Leader，我想在看板上看到按人/项目维度的周进度，以便发现进度异常 | S | 可视化是 Leader 的核心使用场景 |
| 4 | 团队管理 | 作为 Leader，我想创建团队并邀请成员，以便团队成员在同一空间协作 | S | 多人协作的基础设施 |
| 5 | 飞书通知推送 | 作为 Leader，我想在飞书收到 AI 汇总通知，以便不用打开新工具 | S | 降低使用门槛，融入现有工作流 |

**象限修正记录**：原清单第 6 项「Git 提交自动关联」阶段三初判为 L（需 OAuth + 多平台适配），阶段五评估后**降级为二期**，一期用"手动粘贴 PR 链接"替代。

## 5. 核心用户旅程

### 旅程：Leader 查看 AI 日报汇总

角色：技术团队 Leader
目标：快速掌握团队今日进展

步骤：
1. 系统 → 每日 20:00 自动触发 AI 汇总
2. 系统 → 将汇总结果推送到 Leader 的飞书
3. 用户 → 在飞书中点击链接，跳转到 TeamLog 看板
4. 用户 → 浏览 AI 摘要：关键进展（3-5条）、阻塞项（标红）、风险预警
5. 用户 → 点击某条阻塞项，查看原始日报详情
6. 用户 → 在阻塞项下方 @相关人员并留言
7. ✅ 完成：Leader 5 分钟内完成团队状态检视

**异常分支（三类必备）**：

| 类型 | 处理方式 |
|------|---------|
| **首次使用 / 空状态** | 团队刚建、无任何日报时，看板显示引导卡片："先邀请 3 位成员 → 今晚 20:00 你会收到第一份汇总"，并提供一键复制的邀请文案 |
| **关键步骤失败** | AI 汇总生成失败（API 超时/限流）→ 降级为按人分组的原始日报列表 + 顶部提示"AI 摘要生成失败，已展示原文，可手动重试" |
| **中途退出后恢复** | 开发者填报到一半关闭页面 → 本地草稿自动保存，次日打开自动恢复并提示"你有一份未提交的昨日日报" |

**补充分支**：当日日报提交不足 50% → 汇总中标注"数据不完整"，并通知未提交成员

## 6. 成功指标

| 类型 | 指标 | 一期目标值 | 怎么采集 |
|------|------|----------|---------|
| 🌟 北极星指标 | **周活跃 Leader 查看汇总次数**（反映核心价值被消费的频次） | ≥ 4 次/周/团队 | 汇总页 PV 埋点，按团队去重 |
| 辅助指标 | 团队日报提交率 | ≥ 70% | 提交人数 / 团队人数 |
| 辅助指标 | 第 4 周团队留存率 | ≥ 60% | 首周激活团队中第 4 周仍有汇总消费的比例 |
| 辅助指标 | 开发者填报时长中位数 | ≤ 3 分钟 | 表单打开到提交的时间差 |
| 反向指标 | AI 摘要被 Leader 标记"不准确"的比例 | ≤ 15% | 摘要下方"这条不准"按钮点击率 |

## 7. 可行性评估与技术约束

### 7.1 技术可行性（聚焦项）

| 功能 | 技术可行性 | 潜在风险 | 降级方案 | 象限修正 |
|------|-----------|---------|---------|---------|
| AI 汇总 | ⚠️ 有挑战 | 大模型 API 成本与响应延迟；摘要质量不稳定 | 用小参数模型降本 + 异步生成 + 结果缓存；质量不达标则退到"抽取式摘要（提取阻塞关键词 + 原文引用）" | 维持 MVP |
| Git 提交自动关联 | ⚠️ 有挑战 | 需用户授权 GitHub/GitLab，多平台 OAuth 适配 | 一期手动粘贴 PR 链接 | **降级为二期** |
| 飞书通知 | ✅ 常规实现 | 飞书 API 限流 | Webhook 方式，失败重试 3 次 | 维持 MVP |
| 结构化日报 / 看板 / 团队管理 | ✅ 常规实现 | 无 | — | 维持 MVP |

**成本估算**：按 20 人团队 × 每日 1 次汇总 × 每次约 4K token 计，单团队月成本约 ¥5-15 量级，在预算内。

**合规**：日报内容属企业内部数据，需在隐私说明中明确"不用于模型训练"；MVP 阶段不存储任何个人身份信息以外的敏感字段。

### 7.2 团队与资源评估

| 维度 | 现状 | 风险等级 | 建议 |
|------|------|---------|------|
| 团队规模 | 2 人（1 全栈 + 1 半职设计） | 中 | 只做 Web 端，复用现成组件库，不做定制设计 |
| 技术能力匹配度 | React + Node 熟悉；大模型调用做过 demo | 低 | — |
| 时间约束 | 期望 4 周上线 vs 估算 5-6 周 | 中 | 砍掉 Git 关联（已执行），进度看板一期只做"按人"维度，"按项目"维度放二期 |
| 预算约束 | 每月 ¥500 以内 | 低 | 模型成本可控，服务器用最小规格 |

## 8. 冷启动与分发路径

| 维度 | 结论 |
|------|------|
| **首批用户获取路径** | ① 创始人自己所在的 3 个技术管理者微信群（约 400 人，估计能触达 15-20 个 Leader）；② 一对一冷启：找 10 位认识的技术 Leader 直接演示 |
| **触达成本** | 免费，主要成本是时间（约 2 周、每天 1-2 次沟通） |
| **说服门槛** | 高：Leader 认可后还需**说服整个团队改变填报习惯**——这是最大的坎。应对：支持"先只让 3 个人试用"的小范围模式，不要求全团队切换 |
| **平台依赖风险** | 中：通知链路依赖飞书 Webhook。飞书若收紧机器人策略，退路是邮件 + 站内消息；后续补钉钉/企微 |
| **一期分发假设** | 最关键假设："Leader 愿意为此推动团队改变填报习惯"。最小验证：找 5 位 Leader 演示原型，看有几位愿意当场拉群试用（≥2 位视为通过） |

## 9. 明确排除项（Not Doing）

| 不做 | 为什么 |
|------|-------|
| 移动端 App | Leader 的核心场景是"下班后在电脑上看汇总"，飞书内嵌网页已够用 |
| 多语言支持 | 首批用户全部为中文团队，做了没人用 |
| 周报/月报自动生成 | 日报数据积累不足时生成的周报没有价值，等日报跑通再做 |
| 私有化部署 | 2 人团队交付不起私有化的实施与运维成本 |
| Git 提交自动关联 | 阶段五评估为 L 档，会挤掉核心功能的工期，二期做 |
