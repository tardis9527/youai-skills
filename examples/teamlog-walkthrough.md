# TeamLog 体验教程：从想法到 PRD 与原型方案

[English](./teamlog-walkthrough_en.md) · [返回首页](../README.md) · [安装指南](../docs/usage-guide.md)

本教程提供可复制的输入、文档交接步骤和人工检查点。TeamLog 是虚构产品；现有样例是人工编写的精简结构参考，本教程也不是一次真实运行的记录。实际生成内容和耗时取决于模型、工具与回答质量。

## 准备

选择一种方式即可：

- **纯文本对话：** 每一步打开对应 Skill 的完整定义，复制全文到新对话，再发送需求。交接时粘贴上一阶段的完整产物；保存文件需手动完成。
- **AI IDE：** 按 [安装指南](../docs/usage-guide.md) 安装，在一个新的演示项目中操作。下面以 Codex 的 `$skill-name` 为例；Claude Code / Windsurf 改用 `/skill-name`，Cursor 按其 Skill 选择入口调用。

建议每个阶段开启新对话，只调用当前阶段的 Skill，通过文档交接。不要在有真实业务数据的项目里直接试运行演示。

本轮只生成文档、线框和出图提示词，不需要图片接口。若安装包来自已发布的 GitHub 版本，本教程可以作为独立输入使用。

## 第一步：定义产品与 MVP

完整定义：[product-discovery](../skills/02_product-discovery.md)。安装后发送以下内容；纯文本对话省略第一行的调用名：

```text
$product-discovery
我想做 TeamLog：一个面向 10–50 人技术团队的日报助手，
让技术负责人更快看到关键进展、阻塞和风险。
请按 Express 模式帮我梳理目标用户、痛点和 MVP。

以下是演示设定，尚未经过真实用户验证：
- 一期只做 Web，成员填写日报，负责人查看汇总。
- 暂不做 Git 自动关联、移动 App 和复杂企业权限。
- 首批用户计划通过技术管理者社群访谈招募，尚未实际招募。
- AI 汇总失败时应能查看原始日报。

请按阶段追问并让我确认关键范围；不确定的内容保留为未验证假设。
本次演示将最终简报保存为 doc/TeamLog_Brief.md，供下一步读取。
```

根据实际情况回答追问，别直接接受所有推荐。比如“首批用户从哪里来”和“负责人是否愿意换工具”应记录验证计划，而不是写成事实。

确认后检查：

- 主要用户是谁，现有替代方案是什么？
- MVP 是否与排除项清晰分开？
- 是否覆盖空状态、汇总失败和填写中断后的恢复？
- 成功指标是否说明怎么采集，关键假设是否有验证方法？

预期交接文件：`doc/TeamLog_Brief.md`。纯文本对话中，手动保存这一文件或复制完整简报给下一阶段。

[对照现有产品简报样例](./example-product-discovery.md)。其中目标值属于虚构产品设定，不是实测收益。

## 第二步：生成可评审的 PRD

完整定义：[prd-generation](../skills/04_prd-generation.md)。在新对话中发送：

```text
$prd-generation
读取 doc/TeamLog_Brief.md，按 Standard 模式生成 TeamLog 的 PRD。
先检查输入是否包含背景、用户、功能和范围，再确认关键技术决策。
沿用已确认的 MVP；新增建议必须单独标注并让我确认。
特别检查角色权限、日报提交与编辑、AI 汇总失败后的降级行为。
让每个功能能对应到验收标准、数据、接口、页面与关键状态。
未确认项保留在开放问题表，文档保持草稿或评审中。
本次演示将最终文档保存为 doc/TeamLog_PRD.md。
```

纯文本对话：先粘贴完整 Skill 定义和已确认的简报，再发送上面的需求；用“以下简报全文”代替文件读取指令。

按检查点确认技术栈、权限与范围，再继续各章节。重点检查：

- 负责人和成员能读取、修改哪些数据？
- 日报何时允许编辑，编辑后是否需要更新摘要？
- 汇总失败、提交不足和重复提交时怎么办？
- 是否混入了排除项或未经确认的新功能？
- 每个验收条件是否能通过操作或测量判定？

预期交接文件：`doc/TeamLog_PRD.md`。如仍有开放问题，把它们一并交给原型阶段。

[对照现有 PRD 节选](./example-prd-generation.md)。该样例并非当前完整 14 章模板的合格成品，不能用它替代本轮完整 PRD。

## 第三步：设计页面、状态和统一风格

完整定义：[prototype-design](../skills/07_prototype-design.md)。在新对话中发送：

```text
$prototype-design
读取 doc/TeamLog_PRD.md，为 TeamLog 设计一期 Web 原型方案。
先确认上下文和页面范围，再确认统一风格、线框和提示词。
优先覆盖登录、进度看板、日报填写、摘要详情；
如 PRD 的核心流程需要其他页面，请先指出并确认。
覆盖正常、空、加载、失败以及填写中断恢复等相关状态。
输出功能与页面的对应关系、统一设计 Token、线框和交互说明，
以及复用同一 Style Anchor 的中英双语出图提示词。
本轮仅输出文档与提示词，不调用图片接口、不生成真实图片。
将方案保存为 doc/TeamLog_Prototype.md。
```

纯文本对话：提供完整 Skill 定义和 PRD 全文后，以文字描述代替文件读取指令。

重点检查：

- 每个核心功能是否有页面入口，权限是否与 PRD 一致？
- 加载、失败、无数据和恢复流程是否有明确反馈？
- 页面是否共享同一个 Style Anchor ID / 版本及设计 Token？
- 线框中的按钮、文案和交互是否可用于后续实现？

[对照现有原型方案节选](./example-prototype-design.md)。其中提示词尚未配套真实生成图片；AI 图片也不能替代交互与可访问性实现。

## 保存与检查

本次演示约定三个便于交接的文件名；Skill 默认文件名还包含日期和版本，日常项目可沿用其默认规则。

```text
doc/
├── TeamLog_Brief.md
├── TeamLog_PRD.md
└── TeamLog_Prototype.md
```

在克隆的 `youai-skills` 仓库根目录运行以下命令，将路径换成实际演示项目中的文件路径：

```powershell
pwsh ./scripts/validate-product-artifact.ps1 -Path 'D:\demo\doc\TeamLog_PRD.md' -Type PRD
pwsh ./scripts/validate-product-artifact.ps1 -Path 'D:\demo\doc\TeamLog_Prototype.md' -Type Prototype
```

校验器检查结构和未解释占位符；通过不代表需求、数据或设计已验证。只有阶段产物完成后再运行，现有精简样例不保证通过完整产物校验。

## 把一次体验整理为实际案例

记录工具与模型版本、Skill 所用仓库版本、输入、关键回答、三个完整产物、人工修改和剩余问题。若记录耗时，区分人工交互时间与模型等待时间。

可录制 60–90 秒演示：一句需求 → 关键追问 → MVP → 一条功能的验收标准 → 线框与失败状态。只展示真实完成的内容，截图和录屏中隐藏敏感信息。
