# 渐进式音乐创作探索

完整创作时使用。借鉴 `product-discovery` 的学习加载、分档节奏、阶段产物/通过条件、关键假设和回写机制；音乐的判断对象是表达与听感，不照搬产品的功能清单、固定轮次或每阶段审批。

## 为什么先探索，再展开整首歌

用户说的是感受，制作人需要确定可以执行的音乐决定。常见错位是：把“悲伤”直接写成慢钢琴，把“爆款”写成重复口号，把自己的审美当用户审美，或只优化提示词而没检查歌曲究竟在说什么。

采用三层工作次序：

1. **表达任务**：谁在什么处境对谁说什么，希望对方听完有什么变化。先确定这首歌值得存在的原因。
2. **作品身份**：叙述者口吻、情绪矛盾、具体细节、可辨认的词/曲/声音；决定它为何属于这位创作者。
3. **使用与实现**：听众怎样遇到、使用并继续听这首歌，模型怎样接收输入。传播与技术为前两层服务。

创作建议而非经验证的成功定律。每个判断保留来源；没有真实音频时，不宣称已完成旋律听感验证。

## 与产品探索框架的对应

| 借鉴的机制 | 音乐创作中的执行方式 | 应避免的照搬 |
| --- | --- | --- |
| 灵感卡片 | 一句话命题、表达对象、情绪终点和硬约束 | 还没听懂就写整首歌词 |
| 用户画像 | 创作者/音乐人设/本首叙述者/目标听众分开 | 用年龄或用户职业代替听众处境 |
| 价值提炼与收敛 | 比较核心句/Hook 与听感，选一个主路线 | 多曲风、多人声、多个高潮全部叠加 |
| 用户旅程 | 初次听见→进入故事→情绪转折→带走一句话/动机→重听 | 所有歌强制三秒高潮或固定结构 |
| 可行性与分发 | 词的密度、时长、演唱难点、模型控制边界、片段使用场景 | 用模型字段替代作曲或承诺传播 |
| Brief / 假设回写 | 统一记录选择、依据、未知和验证；后续发现问题只改受影响部分 | 方向变了却继续沿用旧歌词或旧描述 |

## 三档实际节奏

以入口 `SKILL.md` 的路由和选档表为准。Standard 是新创作默认档；从零写歌词、给原词配曲、从零设计 Caption/Style 也属于新创作。“快速”“今晚用”“其余你定”单独出现不触发 Express；明确“不要问，直接出完整稿”“跳过咨询”等才允许跳过分步了解。Deep 增加比较与检验，不改变交稿条件。

| 环节 | Express | Standard | Deep |
| --- | --- | --- | --- |
| 开场 | 已知提取；只有权限或硬约束冲突才补问 | 只问最早一个未解决维度，给推荐后等待 | 先识别创作主张和人设/项目目标 |
| 方向 | 一个推荐，委托范围内直接采用 | 两个有差异的核心句/听感提案 | 2–3 个路线，说明各自适用与牺牲 |
| 展开前 | 简报与方案合并 | 覆盖相关维度后，整合 Brief 并等用户确认展开 | 可先用很短的 Hook 验证口吻，再确认 Brief |
| 检查 | 一次聚焦自查 | 词曲/约束自查，给一个主要待验证点 | 加入全曲发展、场景适配与反例检查 |
| 反馈 | 按主问题给新版 | 记录改动和对照 | 结合真实听众/平台数据审视原假设 |

**停问规则**：Standard/Deep 在当前问题提出后停止，等待真实回答；回答只解决其实际涉及的维度。覆盖检查完成后单独展示整合 Brief 并问是否展开，得到这次确认才停止采访、进入完整生成。仅一个问答、选中核心句、选择女声或接受木吉他推荐，都不能代替覆盖检查与交稿确认。Express 已有明确直出授权时不再要求重复确认。

已明确的维度直接复用，不为凑轮数重复问；模型推断和制作人建议不算已解决。某一项“你定/都可以”只委托上个问题限定的范围，记录后继续其他未决维度。单独“加速”压缩说明与选项，不自动取消咨询；用户中途明确要求“不要再问，直接出稿”才切 Express。方向变化只重开受影响的维度。

完整有人声歌曲的特殊人声选择属于 D4，可多选或都不要，不为三个元素各开一轮；但不能挤到用途、主题、曲风同一个大问卷里。未答记 `pending`，不得写成拒绝。已明确、该项明确委托、纯器乐及局部任务按入口规则跳过。无歌词但人声范围不明时先解决纯器乐/无词人声的区别。

## 按维度推进，而不是问过一次就放行

以下是内部覆盖清单，不一次发给用户。先从现有信息填值；默认按顺序选择最早的未决维度，每轮只讨论该维度。用户提前提供后续维度信息时照实记录，不强迫重答。

| 阶段 | 需要了解的创作选择 | 本轮可用的一问示例 | 阶段后去向 |
| --- | --- | --- | --- |
| D1 用途与对象 | 给谁、在哪里听，歌曲主体或背景，最想带来的结果；有词/无词/纯器乐边界 | “这首主要是送给朋友私下听，还是给毕业短片用？” | 继续 D2，不能直接写整首 |
| D2 表达与歌词 | 主题/视角/情绪终点，故事或抽象表达，歌词语言与原词/代写权限 | “你更想表达舍不得，还是不挽留的祝福？” | 继续 D3；缺素材可另轮补最必要细节 |
| D3 曲风与旋律听感 | 主风格、律动/速度感、记忆点与旋律气质，喜欢/不喜欢的声音或参考维度 | “你更想贴近私下倾诉，还是轻快到能一起跟唱？” | 继续 D4；不要替用户默认整套制作 |
| D4 演唱与表演 | 人声配置/音色/演唱态度；需要时区分旁白/说唱/衬词；无词人声范围 | “更想要贴近说话的克制演唱，还是副歌明显展开？” | 特殊表演未知时另轮在同维度询问，再去 D5 |
| D5 配器、结构与长度 | 主奏/核心配器、密度与动态，片段或完整曲、目标长度、段落反差、收尾/循环和避雷 | “编制更想保留吉他和人声的留白，还是副歌加入乐队？” | 覆盖完成后到 B；结构长度未知时分轮补，不把整行问完 |
| B 简报确认 | 整合已解决的相关维度、来源和明确委托，指出尚存限制 | “按这份简报展开完整歌词和模型提示词，可以吗？” | 本轮停下；收到针对该问题的明确确认后才生成 |

纯器乐：D2 改为主题/情绪与动机，不问歌词故事；D4 的有词演唱与特殊人声记不适用，将器乐主奏与声部要求放 D5。只交歌词：不需要的模型、音色和配器细节可记不适用，但用途、表达、语言/内容权限及必要可唱性仍需明确。B 只请求本次范围内的展开，不额外推销双模型。

B 可以带少量已讨论维度下的制作细化建议，例如短曲的常规段落连接、第二主歌增加新信息，并保留 recommended，待用户随简报一起接受；不能在 B 首次代选此前未讨论也未委托的整个人声、曲风或配器方向，再用一次“可以”补做全部采访。

每个相关维度使用 `unasked / asked / resolved / delegated / not_applicable`。`resolved` 必须来自用户原始要求或真实回答；`delegated` 必须有该范围的明确委托；`not_applicable` 写清与交付范围或纯器乐分支的关系。`recommended/inferred` 的值在被接受前仍是未决，不允许自己把它改为 resolved。一个维度内仍有会改变作品方向的未决选择时，该维度尚未完成；不需要逐个询问全部微观技术细节。

```yaml
consultation:
  status: in_progress
  stage: D2
  dimensions:
    D1: {status: resolved, source: user_explicit, value: "送朋友私下听"}
    D2: {status: asked, source: unknown, value: null}
    D3: {status: unasked, source: unknown, value: null}
    D4: {status: unasked, source: unknown, value: null}
    D5: {status: unasked, source: unknown, value: null}
  pending_question: "更想表达舍不得，还是不挽留的祝福？"
  brief_confirmation: {status: not_requested, evidence: null}
  bypass: {explicit: false, evidence: null, scope: null}
```

这是中途状态示例，不是可直接交稿的默认值。`consultation.status` 与入口的 `consultation_status` 是同一状态，不维护两份矛盾的值。尚有 asked/unasked 的相关选择时继续问；全覆盖后为 awaiting_confirmation；收到 B 的真实回复才为 confirmed。跨轮只保留必要状态，不把内部状态表每轮完整发给用户。

**完整生成判断**：`权限与硬约束无冲突 AND（覆盖完成且 B 已确认 OR 明确要求跳过咨询并完整直出）`。这是行为约束，不是已安装的运行时拦截器；必须由真实多轮试用核对，格式检查不能证明执行遵循。

## 首次咨询回复的硬边界

只要 `consultation_status` 是 `required` 或 `in_progress`，回复保持在当前维度，推荐使用以下结构：

```markdown
已知：你想给离开城市的朋友写歌。
这一步先定用途。我建议先以私下听为主，能容纳更贴近你们的细节。
这首主要是给对方私下听，还是也要配离别短片？
```

问题后结束本轮，不附“下面先给完整草稿”。下一轮先理解回答、更新该维度，再问下一未决项。不得在第一问后承诺“一回答就展开完整稿”，除非其余维度确实已解决，且该问就是 B 的交稿确认。

可以复述用户原话，但不要把推荐写成“你的要求”。例如“副歌加入童声叠唱”“不加入 Rap、旁白或 Ad-lib”在用户没有明确说过或确认前，分别只能标为 `recommended` 与 `pending`，不能写成已确定。单独的“好”“可以”只确认它所回答的提案，不能提升为其他未提及的创作选择。

## 下一问怎么选

先检查上下文和记忆，再用“答复是否会改变创作路线”筛选问题，优先补高影响、高不确定的缺口；技术细节和可逆的小决定留给制作人。

| 用户说法 | 优先探明 | 可以这样给推荐与取舍 |
| --- | --- | --- |
| “写首关于失恋的歌” | 对谁说；是挽回、怨、告别还是自我和解 | “我倾向写告别后的松一口气，情绪能往前走；如果你更想保留不甘，我们就不急着释怀。” |
| “治愈、别太俗” | 被理解、被鼓励还是安静陪伴 | 用“替你撑一下”和“陪你坐一会儿”两个口吻对比，避免只换风格标签 |
| “要高级、有质感” | 讨厌什么：过密、夸张唱法、套路词或混响过重 | 先给克制编制/具体歌词的例子；不把高级等同爵士和弦、英文或冷淡 |
| “洗脑一点” | 想让人记住哪句话/节奏，是否方便跟唱 | 推荐短动机与有意义的复现；代价是信息密度降低，不无意义堆重复 |
| “想做抖音爆款” | 谁在何种视频里用，想带走什么感受 | 先找一个具体可用场景；无法得知当前榜单时不假装研究过 |
| “像这首一样” | 用户喜欢的是叙述口吻、律动、音色还是起伏 | 只取已说明或实际听到的维度，再给本作品自己的细节与动机 |
| “不感人/不像我” | 命题错、口吻假，还是演唱/编曲过度 | 先对照核心句与真实表达，再决定改词或改制作 |

问题示例只供挑选，不整表发送。每轮 1–2 问，不能在一个问题里藏一串必填项。需要用户选择时，用具体差异帮助判断；不要求懂 BPM、和声或声乐术语。

## 让人设参与，避免人设绑架

| 对象 | 该记录什么 | 不该推断什么 |
| --- | --- | --- |
| 创作者 | 工作节奏、真实偏好、素材边界、愿意长期保留的表达原则 | 职业/年龄自动决定音乐口味 |
| 长期音乐人设 | 用户确认的艺术身份、说话姿态、价值态度、声音倾向及反标签 | 某次选的女声就等于永远女声或可锁定真实声线 |
| 本首叙述者 | 视角、与对象的关系、当下矛盾、最终态度 | 第一人称歌词就是用户自传 |
| 目标听众 | 共同处境、听歌情境、期待与使用场景 | 年轻人都喜欢同一种风格 |

多个 IP 或客户分别用 `persona_id`；当前身份不明且会造成串档时只澄清身份。没有长期人设就先做作品，不强制创建 IP。新项目需要跨项目记忆时，只读用户指定的档案，不自动扫描其他目录。

## Music Brief（按规模裁剪）

一份简报贯穿创作并嵌入最终提示词文档，不强制另建文件。阶段间先用几行摘要，Deep 或长项目才保留进度表。

```markdown
## Music Brief

- work_id / version / persona_id：
- 节奏与当前进度：Express / Standard / Deep；`consultation_status`: required / in_progress / awaiting_confirmation / confirmed / delegated；当前 D1–D5 / B；下一待答项
- 维度覆盖：各项 resolved / delegated / not_applicable 的值与来源；未决项保持 unasked / asked；Brief 的交稿确认证据或明确直出授权
- 一句话命题：谁借什么处境，对谁表达什么
- 主用途 / 次用途 / 音乐角色：
- 本首叙述者 / 目标听众与情境：
- 听后希望感到、记住或做什么：
- 故事情绪 → 演唱态度 → 音乐能量：
- 素材与权限 / 必须保留 / 避免：
- 形式与目标长度：
- 描述 / 歌词 / 演唱语言及来源：描述默认英文（recommended），用户指定优先；后两项遵循作品选择
- 歌词 / 人声范围：有词或无词；无人声 / 仅无词人声 / 有词人声
- 特殊人声选择：not_applicable / not_asked / pending / selected / declined / delegated；选中/拒绝元素、来源与内容权限
- 人设中本次沿用的特征：未建立则写“不适用”
- 路线 / 核心句或主 Hook / 听感推荐与取舍：
- 成功标准：表达一项、音乐/结构一项，公开传播时再加场景一项

| 关键选择/假设 | 来源或证据 | 状态 | 若错了影响什么 | 最小验证 |
| --- | --- | --- | --- | --- |
| ... | user_explicit / inferred / recommended / unknown | confirmed / delegated / unverified | ... | ... |
```

不要把推荐默认标为 confirmed；用户选中一个文本方案也不等于其音乐听感已验证。成功标准要能检查，如“核心句能表达不舍又不挽留”“第二主歌增加新信息”；“好听、爆款、用户喜欢”需要后续证据，不能作为已通过的文本项。

## 断点与回写

长项目把当前阶段、已确认选择、最后一项待答和产物路径放进现有文档的进度区，不复制私人对话全文。续作时先读最近版本，不让用户重答。

若“副歌像控诉”源自口吻不符，回写叙述者/情绪终点，并同步核心句、表演与编曲；若只是导出错误，不动创作简报。每次记录改变的是哪项假设、依据是什么、结果是否已听到，形成可追溯的学习。
