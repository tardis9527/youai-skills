# 渐进式音乐创作探索

完整创作时使用。借鉴 `product-discovery` 的学习加载、分档节奏、阶段产物/通过条件、关键假设和回写机制；音乐的判断对象是表达与听感，不照搬产品的功能清单、固定轮次或每阶段审批。

## 为什么先探索，再展开整首歌

用户说的是感受，制作人需要确定可以执行的音乐决定。常见错位是：把“悲伤”直接写成慢钢琴，把“爆款”写成重复口号，把自己的审美当用户审美，或只优化提示词而没检查歌曲究竟在说什么。

采用三层工作次序：

1. **表达任务**：谁在什么处境对谁说什么，希望对方听完有什么变化。先确定这首歌值得存在的原因。
2. **作品身份**：叙述者口吻、情绪矛盾、具体细节、可辨认的词/曲/声音；决定它为何属于这位创作者。
3. **使用与实现**：听众怎样遇到、使用并继续听这首歌，模型怎样接收输入。传播与技术为前两层服务。

创作建议而非经验证的成功定律。每个判断保留来源；没有真实音频时，不宣称已完成旋律听感验证。

## 与产品探索框架的对应

| 借鉴的机制 | 音乐创作中的执行方式 | 应避免的照搬 |
| --- | --- | --- |
| 灵感卡片 | 一句话命题、表达对象、情绪终点和硬约束 | 还没听懂就写整首歌词 |
| 用户画像 | 创作者/音乐人设/本首叙述者/目标听众分开 | 用年龄或用户职业代替听众处境 |
| 价值提炼与收敛 | 比较核心句/Hook 与听感，选一个主路线 | 多曲风、多人声、多个高潮全部叠加 |
| 用户旅程 | 初次听见→进入故事→情绪转折→带走一句话/动机→重听 | 所有歌强制三秒高潮或固定结构 |
| 可行性与分发 | 词的密度、时长、演唱难点、模型控制边界、片段使用场景 | 用模型字段替代作曲或承诺传播 |
| Brief / 假设回写 | 统一记录选择、依据、未知和验证；后续发现问题只改受影响部分 | 方向变了却继续沿用旧歌词或旧描述 |

## 三档实际节奏

以入口 `SKILL.md` 的选档表为准，不为选档专门发问。Standard 是完整歌曲创作默认档；信息很多、素材完整或已经给出 BPM/曲风/乐器，都不能单独触发 Express。Express 只由明确的快速交稿授权触发。Express 压缩展示与确认，不省略意图、授权和真实性；Deep 增加比较与检验，不增加无关问题。

| 环节 | Express | Standard | Deep |
| --- | --- | --- | --- |
| 开场 | 已知提取；只有高影响缺口才问 | 先列已确认、推荐、待确认，再问最可能写偏的 1–2 个缺口 | 先识别创作主张和人设/项目目标 |
| 方向 | 一个推荐，委托范围内直接采用 | 两个有差异的核心句/听感提案 | 2–3 个路线，说明各自适用与牺牲 |
| 展开前 | 简报与方案合并 | 简报准确后比较 Hook | 可先写短副歌/关键段验证口吻，再展开 |
| 检查 | 一次聚焦自查 | 词曲/约束自查，给一个主要待验证点 | 加入全曲发展、场景适配与反例检查 |
| 反馈 | 按主问题给新版 | 记录改动和对照 | 结合真实听众/平台数据审视原假设 |

**停问规则**：Express 只有在用户明确授权直接交稿，且权限/硬约束无冲突时才可继续；Standard/Deep 必须至少完成一个咨询闸门，不能因信息充分而跳过。闸门通过后，已能提出一致且有区分度的方案，且权限/硬约束无冲突，即可继续；不要求所有表格字段齐全。用户说“不知道/你决定”只表示可以在该范围内推荐，若未同时说“直接出稿/不要问”，仍先完成一次咨询并标记 `delegated` 或 `recommended`，不把沉默当作确认。

只有会改变主题、口吻、歌词权限、主用途或关键听感的决定才值得设确认点。摘要已确认的内容不用再停。用户中途改档、改方向，沿用仍有效的部分，同步回写 Brief、歌词、段落和模型描述。

完整有人声歌曲的特殊人声选择合并到 Standard/Deep 的展开前确认点，只问一次 Spoken Word / Rap Verse / Ad-lib，可多选或都不要；不为三个元素各开一轮。用户未回答时写 `pending`，不得写成拒绝。已明确、明确委托直接出稿、纯器乐及局部任务按入口规则跳过。无歌词但人声范围不明时，先解决纯器乐/无词人声的区别，不能先推销三类有词元素。

## 首次咨询回复的硬边界

只要 `consultation_status` 是 `required` 或 `in_progress`，首次回复应保持可审计而非直接交稿，推荐使用以下结构：

```markdown
### 已确认（user_explicit / user_confirmed）
- 只列用户明确说过的事实与硬约束

### 我的推荐（recommended）
- 只给 1 个主路线，说明它如何服务表达目标及代价

### 待你确认（unknown / pending）
- 只列会改变主题、口吻、歌词权限、主用途或关键听感的 1–2 项

请先确认上面的方向；确认后我再展开完整歌词、模型提示词和参数。
```

可以复述用户原话，但不要把推荐写成“你的要求”。例如“副歌加入童声叠唱”“不加入 Rap、旁白或 Ad-lib”在用户没有明确说过或确认前，分别只能标为 `recommended` 与 `pending`，不能写成已确定。

## 下一问怎么选

先检查上下文和记忆，再用“答复是否会改变创作路线”筛选问题，优先补高影响、高不确定的缺口；技术细节和可逆的小决定留给制作人。

| 用户说法 | 优先探明 | 可以这样给推荐与取舍 |
| --- | --- | --- |
| “写首关于失恋的歌” | 对谁说；是挽回、怨、告别还是自我和解 | “我倾向写告别后的松一口气，情绪能往前走；如果你更想保留不甘，我们就不急着释怀。” |
| “治愈、别太俗” | 被理解、被鼓励还是安静陪伴 | 用“替你撑一下”和“陪你坐一会儿”两个口吻对比，避免只换风格标签 |
| “要高级、有质感” | 讨厌什么：过密、夸张唱法、套路词或混响过重 | 先给克制编制/具体歌词的例子；不把高级等同爵士和弦、英文或冷淡 |
| “洗脑一点” | 想让人记住哪句话/节奏，是否方便跟唱 | 推荐短动机与有意义的复现；代价是信息密度降低，不无意义堆重复 |
| “想做抖音爆款” | 谁在何种视频里用，想带走什么感受 | 先找一个具体可用场景；无法得知当前榜单时不假装研究过 |
| “像这首一样” | 用户喜欢的是叙述口吻、律动、音色还是起伏 | 只取已说明或实际听到的维度，再给本作品自己的细节与动机 |
| “不感人/不像我” | 命题错、口吻假，还是演唱/编曲过度 | 先对照核心句与真实表达，再决定改词或改制作 |

问题示例只供挑选，不整表发送。每轮 1–2 问，不能在一个问题里藏一串必填项。需要用户选择时，用具体差异帮助判断；不要求懂 BPM、和声或声乐术语。

## 让人设参与，避免人设绑架

| 对象 | 该记录什么 | 不该推断什么 |
| --- | --- | --- |
| 创作者 | 工作节奏、真实偏好、素材边界、愿意长期保留的表达原则 | 职业/年龄自动决定音乐口味 |
| 长期音乐人设 | 用户确认的艺术身份、说话姿态、价值态度、声音倾向及反标签 | 某次选的女声就等于永远女声或可锁定真实声线 |
| 本首叙述者 | 视角、与对象的关系、当下矛盾、最终态度 | 第一人称歌词就是用户自传 |
| 目标听众 | 共同处境、听歌情境、期待与使用场景 | 年轻人都喜欢同一种风格 |

多个 IP 或客户分别用 `persona_id`；当前身份不明且会造成串档时只澄清身份。没有长期人设就先做作品，不强制创建 IP。新项目需要跨项目记忆时，只读用户指定的档案，不自动扫描其他目录。

## Music Brief（按规模裁剪）

一份简报贯穿创作并嵌入最终提示词文档，不强制另建文件。阶段间先用几行摘要，Deep 或长项目才保留进度表。

```markdown
## Music Brief

- work_id / version / persona_id：
- 节奏与当前进度：Express / Standard / Deep；`consultation_status`: required / in_progress / confirmed / delegated
- 一句话命题：谁借什么处境，对谁表达什么
- 主用途 / 次用途 / 音乐角色：
- 本首叙述者 / 目标听众与情境：
- 听后希望感到、记住或做什么：
- 故事情绪 → 演唱态度 → 音乐能量：
- 素材与权限 / 必须保留 / 避免：
- 形式与目标长度：
- 歌词 / 人声范围：有词或无词；无人声 / 仅无词人声 / 有词人声
- 特殊人声选择：not_applicable / not_asked / pending / selected / declined / delegated；选中/拒绝元素、来源与内容权限
- 人设中本次沿用的特征：未建立则写“不适用”
- 路线 / 核心句或主 Hook / 听感推荐与取舍：
- 成功标准：表达一项、音乐/结构一项，公开传播时再加场景一项

| 关键选择/假设 | 来源或证据 | 状态 | 若错了影响什么 | 最小验证 |
| --- | --- | --- | --- | --- |
| ... | user_explicit / inferred / recommended / unknown | confirmed / delegated / unverified | ... | ... |
```

不要把推荐默认标为 confirmed；用户选中一个文本方案也不等于其音乐听感已验证。成功标准要能检查，如“核心句能表达不舍又不挽留”“第二主歌增加新信息”；“好听、爆款、用户喜欢”需要后续证据，不能作为已通过的文本项。

## 断点与回写

长项目把当前阶段、已确认选择、最后一项待答和产物路径放进现有文档的进度区，不复制私人对话全文。续作时先读最近版本，不让用户重答。

若“副歌像控诉”源自口吻不符，回写叙述者/情绪终点，并同步核心句、表演与编曲；若只是导出错误，不动创作简报。每次记录改变的是哪项假设、依据是什么、结果是否已听到，形成可追溯的学习。
